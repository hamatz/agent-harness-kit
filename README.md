# agent-harness-kit

**自律型AIエージェント時代におけるソフトウェア工学の再定義** —— 論文と、そのまま使えるスターターキット。

AIエージェントにコードを書かせるとき、信頼の拠り所を「モデルの賢さ」から「検証の仕組みの厳格さ」へ移す。そのための考え方（Harness・Loop・Graph の3層、記憶を持たない査読、失敗を回帰免疫テストへ昇格させる自己学習ループ）を論文にまとめ、雛形と、実際に動く検証コードを添えました。

## まず5分で試す

「AIの『直しました』」ではなく「機械が測った結果」で判断するとはどういうことかを、実際の失敗表示で確かめられます。

```sh
npm ci
npx playwright install --with-deps chromium
npm run demo
```

組版ツールの処理を1か所わざと壊し（AIが別の修正のついでに壊した、という想定）、判型4種×縦書き・横書きの8通りで検査します。壊れた4通りだけが、何を期待して何が観測されたか（EXPECTED / SAW）付きで落ち、壊していないツールは8通りすべて通ります。

## `kit/` の中身

| ファイル | 役割 |
| --- | --- |
| `AGENTS.md` | エージェントへの指示。機械が強制していることの索引と、機械化できない規範の残余だけを書く |
| `SPEC.md` | 仕様と不変条件。人間が必ず読んで承認する |
| `PLAN.md` | 作業の進捗。会話ログではなくここに状態を残す |
| `PROMPTS.md` | 企画の壁打ちから最初のマージまで、各段階でエージェントに渡す文面の例（EGM を使う場合と使わない場合） |
| `LESSONS.md` | 失敗の記録。修正の置き場所（Rung）と、ガードの作動確認（Proof）まで残す |
| `tests/verify_ui.mjs` | UI の汎用検証。ブラウザのエラー（コンソール、未捕捉例外、読み込み失敗）を Exit Code で判定する。画面の正しさそのものは、プロジェクトごとに測れる条件を足す（組版の例は `examples/compositor/tests/verify_layout.mjs`） |
| `.github/workflows/verify.yml` | マージ条件にする必須チェック |
| `.github/CODEOWNERS` | テスト・ゲート・仕様の変更に人間の承認を求める |
| `.env.example` / `.gitignore` | 本物の機密を作業領域に置かないための雛形 |

## 導入の手順

各段階でエージェントに渡す文面の例は [`kit/PROMPTS.md`](kit/PROMPTS.md) にあります。

### ぼんやりした企画から始める場合

コードがまだ一行もない状態からの手順です。大事なのは、**エージェントに実装を書かせる前に壁を立てる**ことです。

1. **リポジトリを用意する** —— 新しいリポジトリに `kit/` の中身をコピーし、`.github/CODEOWNERS` の `@your-team` を自分（またはチーム）に置き換えてプッシュする。
2. **エージェント用の資格情報を分ける** —— エージェントには、自分とは別のアカウントか GitHub App を使わせ、リポジトリ設定・ルールセット・ワークフローを変更する権限を与えない。GitHub では自分のプルリクエストを自分で承認できないので、エージェントが自分と同じアカウントで動くと、コードオーナーの承認が意味を持たなくなります。
3. **ルールセットの第一段を設定する** —— 既定ブランチへの直接プッシュを禁止してプルリクエストを必須にし、コードオーナーのレビューを必須にする。バイパスは誰にも許さない（管理者も含む）。
4. **企画を固める**（[PROMPTS 1](kit/PROMPTS.md#1-企画を固める)）—— [EGM プラグイン](https://github.com/google/elephant-goldfish-model)を使う場合は `egm-brainstorm` → `egm-draft` → `egm-review` → `egm-resolve` の順に進め、承認された設計書を `docs/designs/` に置く。使わない場合は、コードを書かない設計セッションと壁打ちして設計書にまとめ、別のセッションに査読させる。
5. **仕様と受入テストを起こす**（[PROMPTS 2](kit/PROMPTS.md#2-仕様と受入テストを起こす)）—— 設計書から `SPEC.md` と受入テスト（この時点ではすべて Red）を作らせ、`verify.yml` のコマンドを決めた技術スタックのものに置き換えさせる。人間が `SPEC.md` とテストを読んでからマージする。
6. **ルールセットの第二段を設定する** —— `verify` が一度通ったら、必須ステータスチェックに加える。ここで壁が揃います。
7. **作業を分けて回す**（[PROMPTS 3〜6](kit/PROMPTS.md#3-作業を分ける)）—— `PLAN.md` にステップを分け、1ステップずつ新しいセッションで実装させ、別の新しいセッションに差分だけを査読させる。不具合は、直す前に再現テストを書かせる。

### 既存のリポジトリに入れる場合

1. `kit/` の中身をリポジトリのルートにコピーする。すでに `AGENTS.md` があれば、第1部・第2部の形に合わせて統合する。
2. `SPEC.md` を、今ある振る舞いのうち「壊れたら困るもの」から書く。EGM を使う場合は、`egm-bootstrap` で既存コードの設計書を起こしてから抜き出すと楽です。
3. `verify.yml` のコマンドをプロジェクトのものに置き換える（置き換えるまで CI は失敗します）。`AGENTS.md` の第2部をプロジェクトに合わせて削る（20〜30行以内）。
4. 上の2・3・6と同じく、資格情報を分けてルールセットを設定する。**ここを設定しないと、どのファイルも「壁」になりません。**
5. 最初の一歩は、次に不具合を直すときに [PROMPTS 6](kit/PROMPTS.md#6-不具合を直す) を使うことです。直す前に再現テストを書かせ、落ちるのを見てから直させます。

### 導入後のチェックリスト

ファイルを置いただけでは何も強制されません。次がすべて満たされて初めて、AIにも人間にも破れない「壁」になります。

- [ ] `verify` ワークフローが既定ブランチで成功している
- [ ] ルールセットで `verify` を必須ステータスチェックにしている
- [ ] ルールセットで「コードオーナーのレビューを必須」にしている
- [ ] ルールセットのバイパスを誰にも許していない（管理者も含む）
- [ ] エージェントが、人間とは別のアカウントか GitHub App で動いている
- [ ] エージェントが使う資格情報（トークンや GitHub App）に、リポジトリ設定・ルールセット・ワークフローを変更できる権限を与えていない
- [ ] エージェントの作業環境に、本物の `.env` や鍵が存在しない（`.gitignore` は誤コミットを防ぐだけで、読み取りは防げません）
- [ ] 最初の回帰免疫テストを、わざと壊した版で落ちることを確かめてから入れた

**注意**
- gitleaks-action は、組織アカウントのリポジトリでは無料のライセンスキー（`GITLEAKS_LICENSE`）が必要です。個人アカウントでは不要です。
- `AGENTS.md` は多くのエージェントツールが読む共通の置き場所です。独自のファイル名を読むツール（`GEMINI.md`、`CLAUDE.md` など）では、そこから `AGENTS.md` を参照させてください。

## このキットが保証すること、しないこと

上のチェックリストを満たしている場合に、

**保証すること**
- 必須チェックを通らない変更は、誰の変更でもマージされない
- テスト・ゲート・仕様の変更には、人間の承認が必要になる
- 作業環境に存在しない機密は、エージェントには読めない
- 組版の例では、判型×組方向の8通りで、図版・表のページまたぎ、章の改ページ、小見出しの取り残しが検出される（印刷時の改ページは対象外）

**保証しないこと**
- テストが測っていないものの正しさ。仕様そのものの誤り、認可の抜け穴、性能の劣化、未知の攻撃などは、テストが通っても残りえます
- テスト自体の網の粗さ。テストが弱ければ、弱いまま通ります（ミューテーションテストや、わざと壊した版での確認で補います）
- 設定を変更できる権限を持つ人やエージェントによる迂回
- ローカルの pre-commit フックやエージェントツール側の拒否設定は、早期警告として有用ですが、迂回できるため壁ではありません

認証・決済・データの削除など、間違えたときの被害が大きい箇所は、テストに加えて人間が差分を読む前提です（論文の第1.2節）。

## Elephant-Goldfish Model（EGM）との関係

Google の [Elephant-Goldfish Model](https://github.com/google/elephant-goldfish-model) プラグインとは、受け持つ段階が違います。併用を前提にしています。

| 段階 | 受け持つもの |
| --- | --- |
| 構想・設計（壁打ち、設計書の起草、記憶を持たない査読、人間の承認、設計書とコードのずれの報告） | **EGM** |
| 設計から仕様へ | 承認された設計書（`docs/designs/`）から `SPEC.md` を起こす |
| 実装・検証（作業領域の壁、Exit Code による判定、差分の査読、コードオーナーの承認） | **このキット** |
| 学習・組織（回帰免疫テストへの昇格、根拠に基づく剪定、組織への展開） | **このキット** |

EGM の Goldfish が査読するのは設計書（とそこから参照されるソースコード）で、変更の差分ではありません。テストや権限による強制も持たないため、「直ったかどうかを測る」部分はこのキットが受け持ちます。詳しくは論文の第3.5節を参照してください。

## 検証コードは、それ自体が検証されている

このリポジトリの CI（`npm test`）は、組版ツールをわざと壊した版を作り、検査が**壊した箇所に対応する組み合わせだけ**を落とすことを毎回確かめます。

| 掛けたツール | 縦組み（4判型） | 横組み（4判型） |
| --- | --- | --- |
| Compositor そのもの | 4/4 合格 | 4/4 合格 |
| 縦組みのページ揃えを止めた版 | 0/4 | 4/4 合格 |
| 横組みの章の改ページを外した版 | 4/4 合格 | 0/4 |
| コード図版をページより高くした版 | 4/4 合格 | 0/4 |
| 縦組みで表と小見出しを次のページへ送らない版 | 0/4 | 4/4 合格 |
| 横組みで表と小見出しを次のページへ送らない版 | 4/4 合格 | 0/4 |

何でも落とす検査も、何も見ていない検査も、ここで弾かれます。経緯は論文の付録5・6にあります。

`npm test` は、論文の英訳が日本語版からずれていないことも確かめます（見出し・表・コード・図の骨格・リンク・数値が一致すること。`scripts/check_translation.mjs`）。
